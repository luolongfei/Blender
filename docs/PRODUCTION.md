# 角色制作与文件管理

## 四类文件

| 类别 | 内容 | 规则 |
| --- | --- | --- |
| 正式工作源 | `work/character.blend` | 唯一日常整合入口 |
| 制作资料 | 图片、纹理、建模脚本、配置、原始参考 | 与主源一起保全 |
| 发布成果 | VRM、对应 Blend、版本与检查说明 | 一组输出对应一份源 |
| 过程文件 | 子代理副本、试验导出、渲染和检查记录 | 整合和备份核验后再归档 |

以上路径均相对于角色目录 `projects/<id>/`。单个 VRM 可以供支持它的软件使用，但不能代替可编辑制作源、必要的脚本和资料。当前模型是本地 Blender 路线，不以 Tripo 生成状态作为最新成果依据。

## 主源和候选

主源文件名固定。子代理在独立副本中工作，不并发写主源，也不把副本直接命名成新的正式主源。

整合者收到成果后，记录修改范围、候选文件、验证条件和剩余问题，再决定是否合入。候选的局部检查通过，不代表整合后的完整角色已经通过。

当前阶段资料中可能同时存在较早主源和较新副本。恢复工作前必须阅读交接状态，不按“最大文件”或“最近修改时间”自动选用。

## 阶段记录

角色状态应明确以下内容：

- 正式工作源的相对路径和 SHA-256。
- 当前工具版本及其锁定信息。
- 待合并成果、来源、是否已经写入主源。
- 预览和正式导出分别对应哪份源，是否已经过期。
- 已检查的内容、检查范围和已知问题。
- 是否暂停写入，以及资产复制和校验是否真正完成。

状态记录不得把“可整合”写成“已整合”，也不得把“已导出”写成“客户已验收”。

## 发布

正式输出使用 `exports/avatar.vrm` 和 `exports/avatar.blend`，并保存同一次发布的文件校验和、工具版本和检查结果。预览文件保持预览标识；用户尚未确认外观、作者信息和使用条件时，不标记为最终交付。

步行、招手等动作和审阅页面可能是独立文件，按交付需要另列。不能假定一个 VRM 已包含制作过程中所有动作和工具。

## 备份与清理

Git 管代码、配置、说明和资产清单。模型与贴图按阶段复制备份，备份与代码提交相对应。本方案不需要 Git LFS；资产是否能超过 100 MB 不影响手动复制方案。

一次阶段备份应包括当前主源、依赖资料和未合并成果。备份校验完成、主源已包含有效修改之后，才评估重复副本和临时产物是否可以归档。原画、独有修改和仅存的一份源文件不能作为缓存清理。

普通制作中不必每次小改都生成一套完整交付包。先检查相关部位和关键帧，阶段整合后再做需要的完整验证与导出。
